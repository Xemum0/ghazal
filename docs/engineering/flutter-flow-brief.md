## What you build (per screen)
- Files in `apps/<client_app|provider_app>/lib/features/<flow_snake>/`: `presentation/<id_lower_underscored>.dart` with the widget `<IdPascal>Screen` (for example `cl_disc_01.dart`, `ClDisc01Screen`; the edge checker finds screens by this name), flow-local pieces under `presentation/widgets/`, providers under `application/` (hand-written Riverpod `Notifier` / `AsyncNotifier`, no codegen), and `<flow>_routes.dart`: delete its first line `// GENERATED STUB` to take it over, keep the two getters (`<flow>Routes`, `<flow>TabRoots`) and the route names (inventory ids), and replace each `GzStubScreen` builder with your screen through `gzScreenPage` / `gzSheetPage` of the kit. A screen of `kind: sheet` is a sheet (`GzSheet` content, the footer pinned, drag to dismiss); `tab-root` screens live in their tab.
- **Data only through repositories.** Providers read the repository providers of `ghazal_app_kit` and the shared state of `lib/app/state` (the contract and names are in `flutter-dev.md`). Never hard-code a venue, price, date or name; never import a mock. A screen opened WITHOUT route params shows the hero story entity (the same default the web `#/frame/<id>` shows: venue V01, the hero request, Reem's first voucher ...), so the harness and the demo tools can open any screen directly; with params it shows that entity.
- **Five states, always.** Every screen handles loading (the skeleton that matches the layout, no spinner on a whole screen), data, empty (illustration + one action), error (retry) and offline through `GzAsyncView`; the inventory `states` list tells which ones the screen needs as frames. No screen may ever render blank, a raw exception, a stack trace or `Not built yet`.
- **Every tap goes somewhere sensible.** Walk the `interactions` and `navigatesTo` lists of the inventory: each target is reached by a real control through the navigator of the kit (`context.gzNav.push('CL-VENU-01', {'venueId': id})`, `openSheet`, `replace`, `switchTab`, `pop`, `toast`), by route NAME only (never import another feature). Guest-gated actions (send a request, get a voucher, book a visit, chat, review, plan, quote, save) call the sign-in gate of the kit with the commit moment and where to resume. Mutations go through the repositories and show their result (toast with undo where the web has it, optimistic where the web is, an error toast with the problem message when the API refuses). Back, close and swipe-back behave like the prototype; a sheet's scrim tap and drag dismiss; the keyboard never covers a field or the primary action.
- **Strings** come from the generated `AppL10n` (`context.l10n.<key>`): the keys are the web keys of `packages/i18n/messages/{en,ar}/<client|hotel>-<flow>.json` and `common`, already merged into the app's ARB (grep the key names the web screen passes to `t(...)`). Never a literal in `Text(`. Never type a price, date, number or phone: `ref.watch(gzFormatProvider)` / `context.gzFormat` formats (money from integer fils, Western digits, Asia/Kuwait). Only a Flutter-only need (an accessible name the web does not have) adds a key, to the same namespace JSON, then `pnpm l10n`; batch such edits (the generator takes a lock).
- **Components.** Build every screen from `ghazal_ui` (core, inputs, nav, overlays, charts, the client / hotel / voucher / visits / filters / provider domain components): `GzScreen` + `GzTopBar` + `GzActionBar`, `GzVenueCard`, `GzBookingThread`, `GzSheet`, `GzEmptyState` ... Look at what the web screen imports from `design/src/system/*` and use its `Gz` twin. A missing component or token: one line to `docs/engineering/requests.md` (`>>`) and a flow-local widget under `presentation/widgets/` meanwhile; never inline a colour or a magic number (tokens only).
- **Motion** as the prototype: the page and sheet transitions come with the router; shared-element expansions (card to gallery), the thread draw-on, favourite pop, tray insertion, skeleton to content cross-fade, success draw, countdown states; reduced motion removes travel and keeps a 120 ms fade. Lists use builder constructors; images go through `GzPhoto` (fixed aspect boxes); `RepaintBoundary` around list cards; no `Opacity` / `BackdropFilter`.
- **Accessibility and RTL**: 44 x 44 targets, Semantics labels and values on every control and card (one node per card), visible focus, contrast by tokens, logical directions only, phones / prices / dates as LTR islands, mirrored chevrons and progress per ADR 0014.

## The loop that proves a screen (mandatory, per screen)
1. `pnpm fshot --app <client|provider> --screen <ID> --lang both` (add `--state loading|empty|error|offline|guest` for each state the inventory lists, and `--w 360 430` for the fluid check) writes `apps/<app>/build/shots/<ID>.<lang>[.<w>][.<state>].png`; then `node tools/parity/parity.mjs --app <client|hotel> --screen <ID> --lang ar` (and `en`) writes the composite `reference | flutter | difference` and the score. Read the Arabic composite with the Read tool (and the English one whenever the score is 0.075 or more or anything looks off).
2. Bar: below 0.075 is clean; 0.075 to 0.12 is acceptable only when the composite shows thin outlines along text and nothing else (the text baseline noise is documented); above 0.12 or any visible box, icon, colour, size or position difference is a defect. Trace it with numbers: `pnpm probe -- --screen <ID> --selector '<css>' --depth 3` prints the web's computed boxes, `tester.getRect` the Flutter ones. At most three fix rounds per screen, then report what remains and why. At 360 and 430 wide there is no overflow stripe, no clipped text, and the layout stays fluid (the gutter 20 holds); at text scale 1.3 (`SHOT_TEXT_SCALE=1.3`) nothing is cut off.
3. The flow test `apps/<app>/test/features/<flow>/<flow>_flow_test.dart`: drives the real router and the in-process mock (`autoRun: false`, `control.flush()`): opens the flow entry, walks the main path with real taps, asserts the navigation outcomes and the data effects (a request sent shows in the list; a decision changes the status), the five states (skeleton, empty, error with retry, offline), the guest gate for a gated action, back and sheet dismissal, and one Arabic run. Bounded, no real IO in fake async.
4. `node tools/check-nav-edges.mjs --app <client|provider> --flow <flow-id> --list` shows no stub and no missing edge for your flow; `bash tools/check-dart-rules.sh <your paths>`; `flutter analyze <your paths>`; your tests green. Update YOUR row of the flow ledger in `docs/engineering/flutter-status.md` (flow, screens done / total, worst parity score, flow test, open issues) with `Edit` on that row only.

## Ownership and coordination
You may create or edit only: `apps/<app>/lib/features/<your flows>/**`, `apps/<app>/test/features/<your flows>/**`, the namespace JSON of your flows under `packages/i18n/messages/**` (Flutter-only keys), your rows of the status ledger, and append-only lines to `docs/engineering/requests.md`. Never `lib/app/**`, never packages, never another flow. If your screen needs data another flow also needs, write your own thin provider over the repository (a duplicate read is cheap) or ask for a shared one in `requests.md`. Another agent's half-written file can break `flutter analyze` for a minute: retry after 60 s. Tests and shots run through the semaphore (`pnpm fshot` and `node tools/with-slot.mjs flutter-test -- ...`), never several by hand in parallel; a test that hangs holds a slot forever, so keep every test bounded.

## Report (structured, honest, short)
Per screen: file, states built, parity ar / en at 390, widths checked, defects traced (with the measured numbers) and fixed; the flow test (count, what it covers); edge check result; l10n keys added; requests filed; anything unfinished, with the reason. Keep the working lean: do not re-read documents summarised here, do not open `feature-matrix.json`, one build pass per screen then at most three fix rounds.
