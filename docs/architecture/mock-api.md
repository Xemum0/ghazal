# The Ghazal mock API (`packages/ghazal_mock_api`)

A pure Dart implementation of the whole REST contract (`packages/contracts/openapi/ghazal.v1.yaml`: 220 operations, 23 tags) over an in-memory database seeded from the prototype's fixtures. It is the backend of both Flutter apps during F2-F4 and the readable, executable specification the NestJS backend is written against (`backend-handoff.md`). Status 2026-10-29 (owner round 2, ADR 0038): all 220 operations served, contract test 220 of 220, engine equal to the TypeScript engine on 2,192 shared cases, and the selection logic (shelves, search, Needs-you, request segments ...) equal to the web on 156 selector cases (312 assertions), 102 Dart tests green. Round 2 added sex on the client account, governorates as the client's region, the partner application and no venue extras (section "Round 2" below).

## Two hosting modes, one code base

**In-process** (apps, simulator, tests; no sockets, nothing to start). `MockBackend.httpClientAdapter` is a dio `HttpClientAdapter`; the shelf handler answers inside the process.

```dart
final mock = await MockBackend.create(
  seed: SeedSource.fromLoader((p) => rootBundle.loadString('packages/ghazal_mock_api/assets/$p')), // apps; tests and the server read the package folder
  persona: 'guest', autoRun: true);
final client = GzApiClient.create(config: cfg, environment: env, tokens: store, adapter: mock.httpClientAdapter);
```

**Standalone** (both apps share one world, so the client-to-partner story propagates; `curl` works):

```
dart run ghazal_mock_api:serve [--port N] [--persona reem] [--scenario slow] [--latency 200] [--clock ISO] [--log]
node tools/ports.mjs url api       # the reserved port: 4701 + 10 * slot (GZ_SLOT); `node tools/ports.mjs check api` verifies identity
```

The server answers `GET /__gz` (the identity handshake of `tools/ports.mjs`: app `api`, slot, rootHash), serves `/v1/*`, `/__mock/*` and the photographs under `/images/`, adds CORS, and stops on `POST /__mock/shutdown`. (`dart run` resolves inside the workspace as it is; this Dart has no `--no-pub` flag.) `MockBackend.serve(port:)` does the same from code and returns a `MockServer` with `url` (the API base, `http://127.0.0.1:4701/v1`).

Base URL in the in-process mode is `http://mock.ghazal.local/v1` (`GzApiConfig` default); the router mounts every path under `/v1`.

* **Sex** (CA-AUTH-14): every seeded client carries `sex` (`female` or `male`); staff accounts have none. A phone the mock has never seen becomes a new, **incomplete** account (placeholder name, no sex, `isNewUser: true` on every sign-in) until `POST /me/complete` (`completeProfile`: name, sex and terms are required) succeeds; `registerAccount` takes name and sex (required) at once. A missing sex is the usual `422 VALIDATION_FAILED` with `errors: [{path: "/sex", code: "required"}]`.
* **Client OTP** (WhatsApp in production) and the **partner email code** follow the same rules. The code is `123456` or any other 6 digits. Three special codes: `000000` is locked (423 `OTP_LOCKED`, `retryAfterSeconds` 900), `111111` is expired (410 `OTP_EXPIRED`), `222222` is wrong (400 `OTP_INVALID` with `params.remainingAttempts`: 4, 3, 2, 1). Anything that is not six digits counts as a wrong code too. Every wrong code uses one of five attempts of that challenge; the fifth is `OTP_LOCKED` and the challenge stays locked, a right code no longer helps (ask for a new one). A new challenge starts again at five. An unknown phone becomes a new client (`isNewUser: true`). More than five codes to one phone inside one story minute is `429 RATE_LIMITED` (the clock is frozen, so a strict 60 s resend rule would lock a demo out).
* **Partner**: email plus password; a new device (unknown `deviceId`) answers `code_required` and the code is `123456` (also in the outbox); the same device then signs in directly. Staff invited by an admin appear in the outbox with an invitation token; accepting it sets their password.
* Social sign-in accepts any identity token; a JWT-shaped token gives `sub`, `email`, `name`. The account has no verified phone, so requests, checkout and chat answer 403 `PHONE_VERIFICATION_REQUIRED` until `verify_phone`.
* Roles are enforced where it matters: staff management is `admin` only, approve/decline/propose/revoke/cancel are `admin` and `manager`, redeeming is `admin`, `manager`, `reception`. A client token on a `/partner/*` route is 403; a partner call needs `X-Venue-Id` or `X-Provider-Id` (or a single membership, or a context chosen with `switchPartnerContext`).
* A persona can also act without a token: `persona: 'reem'` in `create`, `control.setPersona`, or `--persona reem` makes token-less calls act as that persona (what the Demo tools and the shot harness want). `control.sessionFor(persona)` returns real tokens for a `TokenStore`.

## The clock

The story clock starts at `2026-11-12T16:00:00+03:00` (the prototype clock, so countdowns match the design) and moves only through the control surface: `control.setClock(DateTime)`, `control.advance(Duration)` or `POST /__mock/clock {now | advanceDays | advanceHours | advanceMinutes}`. System jobs run lazily at the start of every request and after every clock move (`domain/jobs.dart`): R06 pending expires at `respondBy`, R09 the 24 h window forfeits the voucher, R12 complete at event end plus 12 h, counter-offer expiry (48 h), voucher validity and the 60-day reuse window, unpaid checkout lapse (30 min), visits `arrived` to `completed`, chat read-only after the slot plus 24 h.

Two things use real time because the story clock is frozen: the **mock payment gateway** settles a session after `gatewayDelay` (1.5 s) and the **8 s approval undo window** closes after 8 s (the client hears of an approval only then) and the **scripted chat replies** arrive after `botDelay` (2.5 s). Tests create the mock with `autoRun: false` and call `await control.flush()` to run all of it at once.

## Scenarios and latency

Per call by header, or sticky through the control surface (`setScenario`, `setLatency`, `POST /__mock/scenario {scenario, latencyMs}`):

| Header | Effect |
|---|---|
| `X-Mock-Latency: 800` | adds 800 ms |
| `X-Mock-Scenario: slow` | 1.5 s delay unless a latency is set |
| `error` | `500` problem+json, code `INTERNAL_ERROR` (outside the contract table: fault injection) |
| `offline` | the in-process adapter throws a connection error (`DioException.connectionError`, which `GzApiClient` maps to `ApiProblem.offline()`); the standalone server answers `503` with `X-Mock-Offline: 1` |
| `empty` | every list and page comes back empty (also `getHome` shelves, Today, windows, listings, staff, visit dates and slots) |
| `expired` | the first authenticated call with each access token answers `401 TOKEN_EXPIRED`; the client refreshes once (single flight), replays and carries on |

Other middleware: `X-App-Version` below `1.0.0` is `426 APP_UPDATE_REQUIRED`; `Idempotency-Key` replays the stored answer of the same user, route and body (`Idempotent-Replayed: true`) and a different body is `422 IDEMPOTENCY_KEY_REUSED`; request bodies and query parameters are validated against the contract schemas (`422 VALIDATION_FAILED` with `errors[{path, code}]`); cursors are opaque base64url offsets (`limit` default 20 and **clamped to 1..50 on every list endpoint, never refused**: `limit=500` answers 50 rows, `limit=0` answers 1; only a non-integer is a 422; bad cursor 422); `If-Match` on the 16 flagged operations (a stale request tag is `409 BOOKING_STATE_CONFLICT` with `currentStatus` and `currentVersion`, a stale settings tag is `412 PRECONDITION_FAILED`; the matching `GET`s send `ETag: "vN"`); problem+json with `type`, `title`, `status`, `code`, `requestId`, `params`, `errors`, `alternatives`.

## The control surface (not part of the product API)

In code: `MockBackend.control` (`MockControl`). Over HTTP: `POST /__mock/<name>` with a JSON body (the in-process adapter answers them too, at `http://mock.ghazal.local/__mock/...`).

| `MockControl` | HTTP | Does |
|---|---|---|
| `reset()` | `reset` | seeds again, clock back, no sessions, no pending work (persona, scenario, latency stay) |
| `setClock(at)`, `advance(d)` | `clock` | moves story time and runs the jobs that fall due |
| `setPersona(key)`, `sessionFor(key)` | `persona`, `session` | token-less calls act as the persona; tokens of a persona session |
| `setScenario(s)`, `setLatency(d)` | `scenario {scenario, latencyMs}` | sticky scenario and latency |
| `settlePayment(id, outcome: succeeded \| failed \| cancelled)` | `payments/{id}/settle` | the gateway answers now (succeeded activates the voucher, or moves a paid listing to review) |
| `setGatewayDown(bool)` | `gateway {down}` | new payment sessions answer 502 `PAYMENT_GATEWAY_ERROR` |
| `moderateListing(id, approve:, codes:, note:)` | `listings/{id}/moderate {action: approve \| reject, codes, note}` | Super Admin moderation: pending review to active, or rejected with codes and a note |
| `decidePartnerApplication(id, accept:, reason:)` | `applications/{id}/decide {action: accept \| reject, reason}` | Super Admin decision on a partner application (PA-ACC-07): accept makes the account `active` so it can create listings; reject keeps it `under_review` and stores `reason` (both languages) for the applicant, who can edit and resubmit. Only a pending application can be decided (409 `APPLICATION_NOT_EDITABLE`); an unknown id is 404 |
| `decideRefund(id, grant:, reason:)` | `support/refund-requests/{id}/decide {action: grant \| decline, reason}` | grant creates the credit voucher (original voucher becomes `credit_issued`), decline carries a reason |
| `supportReply(visitId, text:)` | `visits/{id}/support-reply` | a message from Ghazal support in the visit group chat |
| `simulateRival()` | `rival` | the competing request of Dalal for Thu 14 Jan (the web's `simulateCompeting`) goes into the database with its voucher and `requested` claim; idempotent; `reset` takes it out again (see "Seed overlay") |
| `jumpToStory(point)` | `story {point}` | the hero request in one of `storyPoints`: pending, approved, confirmed, redeemed, completed, declined, expired, lapsed, cancelled, counter_offer (booking, voucher, claims and the client notification) |
| `setPlanRate(cycle, fils)` | `plans/{cycle}/rate {ratesFils}` | test hook: while null (the real state) paying a listing is 409 `PLAN_RATES_NOT_ANNOUNCED` |
| `markListingPaid(id, amountFils:)` | `listings/{id}/billing` | test hook: a paid listing, so the fee-refund record can be exercised |
| `flush()` | `flush` | runs the pending gateway, chat-reply and undo-window work now |
| `outbox`, `events`, `state` | `GET outbox`, `events`, `state` | the emails the mock "sent", the event log, a summary for the Demo tools |

`POST /__mock/shutdown` (standalone only) closes the server; `PUT /__mock/uploads/{id}` accepts an upload and stores nothing.

## Seeds, images and the wire

* `tools/export-mock-seed.mjs` writes `assets/seed/<Schema>.seed.json` (47 files, 1.2 MB), `extra.json` (config, personas, billing, hotel settings, hero variants, legal texts) and `manifest.json` from `fixtures-to-wire.mjs` `wireSets()`: the seeds are exactly the wire-mapped fixtures. The only changes are the image convention and moving the hero-story variants (same ids as the stored story rows) into `extra.json`. It also writes `assets/spec/routes.json`, a slim route table (operation, path, status, access, parameters, request schemas) that the mock builds its router and request validation from. `--check` fails when stale.
* **Image convention.** Every `ImageRef` carries `id: <imageId>` and `baseUrl: asset://ghazal_mock_api/images/<imageId>` (`<imageId>` is the file name without extension). `tools/optimize-mock-images.mjs` writes `assets/images/<imageId>_480.jpg` and `_960.jpg` (long edge, quality 76, ImageMagick; 149 photographs, 298 files, 15.9 MB, budget 35 MB). The UI resolves the base by scheme: `asset://ghazal_mock_api/images/<id>` becomes `AssetImage('images/<id>_480.jpg', package: 'ghazal_mock_api')` (or `_960`); any other scheme is a plain network URL with the same suffix (`<base>_480.jpg`). The standalone server rewrites the prefix in every response to `http://host:port/images/` and serves the files. A `MessageImage.file` is a path under the prototype images; its id is the same rule.
* Internal fields of stored documents are prefixed `_` and stripped from every response. Dates are Kuwait civil dates, instants carry `+03:00`, money is integer fils.

## What the mock implements (the rules, readable in `lib/src/`)

`engine/` pure Dart ports (pricing and quotes: standard against voucher price, per person and package, weekday, weekend, holiday, season and special-date tiers, extras, complimentary guests, service charge, voucher windows; availability by day from the deterministic seeded occupancy; voucher codes, QR payload, validity, reuse, the release and credit table; the transition table R01-R14; visit slots; SLA readings; Arabic search normalisation) and `catalog.dart` (search with filters and sorts, card prices, compare, nearby, region search, quotes). `domain/requests.dart` applies R01-R13 with guards, voucher outcomes, calendar claims and notifications; `domain/vouchers.dart` the voucher life cycle (checkout, payment session, activation, bind, release with the 60-day window, redeem, forfeit, expire, credit vouchers); `domain/visits.dart` visits and the three-member group chat; `domain/chat.dart` messages and the scripted replies. Handlers in `handlers/<tag>.dart`, one file per contract tag, keyed by `operationId` (`handlers/handlers.dart`); the router and every status code come from the contract.

**The web's view logic, in Dart** (`engine/discover.dart`, a port of `design/src/screens/client/discover/_components/data.ts` and of the region search of CL-DISC-07; every rule below is pinned by `selector-cases.json`):

* **Home** (`getHome`): the rails in the web's order, `free` (needs a date; one card per hall free on the date in the Brief's areas, held halls are not free here), `featured` (one card: the first paid placement that is not booked on the date), `voucher` (four, largest saving first, the saving beats the KD 2 fee), `week` (**the next seven days, one card per venue on its soonest free day, four by date then id; `date` of the item is that day**), `recommended`, `trending`, `nearby` (always present: the origin is the first Brief area, else Salmiya). `freeCount` is the halls a request can go to on the Brief date **in the Brief's areas, held halls included** (3 for the hero Brief, not the 9 of the whole country) and `null` without a date; `nearestFreeDates` are the three nearest Thursday-to-Saturday dates around the Brief date with a free hall, sorted by date; category counts follow the web's `inCategory`. With no Brief field in the query the signed-in couple's wedding profile is the Brief (date, women's guest count, first audience searched, governorates and the older areas). `governorateIds` (round 2) is the Brief's region: it narrows the `free` shelf, `freeCount` and `nearestFreeDates` exactly like areas did, empty or missing = all; a Brief with governorates ignores its `areaIds`.
* **Search** (`searchVenues`, `countVenues`): the Results list of the web with every filter of the Filters sheet. `availableOnDate` keeps **free and held halls** (the row says `held`); `settings`, `facilities` (`parking`, `valet`, `bridal`, `buffet`, `decor`, `photography`), `brands` (the first word of a hotel name), `perGuestMin/Max` and `voucherPerGuestMin/Max` (fils, compared with the lowest per-guest rate rounded to KD 0.500), `withinMinutes` (drive time from the origin), `arrangement` (the hall sections), `category` and `shelf` (the "See all" of a rail) are new. Round 2: the region is the governorates. `briefGovernorateIds` is the Brief's region and narrows the list by default; an explicit `governorateIds` replaces it, `allAreas=true` (the "All governorates" chip) lifts it and a `shelf` ignores it; empty or missing = all governorates. The older area parameters keep working (deprecated): `briefAreaIds` (default `areaIds`) ranks and narrows a Brief **without** governorates, an explicit `areaIds` replaces it; a Brief with governorates ignores its areas (they neither narrow, rank nor set the origin). The origin of distances is `originId`, else the first Brief area (only when the Brief has no governorates), else Salmiya.
* **Text** (`q` of search, `searchRegions`): `foldSearch` folds tashkeel and tatweel, alef forms, ya and alef maqsura, teh marbuta, hamza seats and **the article** (a leading `ال` of a word of four letters or more, so «المشرف» finds «مشرف» and the other way round): «مشرف» finds Mishref. Region matches are governorates and areas that hold a hall, then halls, in governorate order.
* **Packages for the Brief** (`getVenue`): the price of each package for the hall being booked (`hallId` query, else the first hall of the package that has the Brief's audience): besides `standard`, `voucher`, `savings` the row carries `perGuest`, `flat`, `voucherPerGuest`, `voucherFlat`, `billedGuests`, `billableGuests`, `tier`, `hallId` and `audience`, so the booking flow needs one `getVenue` instead of one `quoteVenue` per package. Quote extras carry a quantity (`extras[{extraId, qty}]` in `quoteVenue` and `createRequest`; the quantity must be 1 up to the extra's `maxQty`, 422 `out_of_range` otherwise; a per-guest extra takes the billable guests).
* **Partner** (the hero partner is Hind, manager at Aurelia Gulf): Needs-you is the queue the web seeds (`needsYou()`): the pending requests (5, nearest deadline first), the approved request waiting for the client, the seeded message, visit request, review and calendar rows; a row of its own is added only for what came up after the story start (a message that began awaiting a reply, a visit asked, a review that turned seven days old), so the old unanswered message of another couple is not a row. Today's `events` are the requests of **the story day** (the venue's booking claims of today in start order), and `tiles.requests` counts requests without a counter-offer out. The request segments are the Bookings tab's: `pending` by deadline, `awaiting_client` by confirm deadline, `upcoming` = confirmed by date then redeemed by date, `past` = ended ones, the last event first. The partner notification list reproduces the web's comparator (notifications of the same minute come out in reverse fixture order: Fatima before Faisal at 11:00); the client list keeps fixture order.
* **Vouchers**: `rebindVoucher` moves a ready voucher (status `active`, tied to its venue or provider) to another date, package, hall or guest count at the same target; what the body leaves out keeps its value (hall when the package sells in it, guests always), a new quote is taken, the voucher stays tied and every request state stays valid. A voucher already attached to a request does not move by itself: the venue's counter-offer (`proposeDates`, `acceptProposal`) is the way.

**Seed overlay** (`db/seeding.dart`): the two places where the mock's story differs from the stored fixtures on purpose. (1) The fixtures carry a second pending request for 14 Jan (Dalal, `competingRequest`); the web adds it only in its Decision screen, so at the story start Aurelia has five pending requests and the rival waits in the collection `Rival` until `simulateRival()` / `POST /__mock/rival`. (2) The hero partner's account also belongs to Aurelia Marina Hall (reception, two requests waiting; `hotel.settings.sister` in the web), which is what makes "Switch venue" appear: `GET /partner/me` lists two memberships (`V01`, `V-sister-marina`) and no active context until the app chooses one (calls without a context are 400 `VENUE_CONTEXT_REQUIRED`, as for any account with several memberships). The sister venue is a name, a role and a count (the web keeps it as state only): venue-bound calls in its context answer 404 for the venue. Staff and invitations carry `invitedByName` (Arabic and Latin) next to the Latin `invitedBy`.

Notes on choices the contract leaves open: a request holds its date as a `requested` claim (not blocking), approval turns it into a `hold` until `confirmBy`, confirmation into a `booking`; approving fails with `SLOT_UNAVAILABLE` if another booking, hold or block took the hall. A counter-offer keeps the voucher price (delta against the voucher total) and leaves the request pending. Credit vouchers bind to the first request and become ordinary bound vouchers. `reportIssue` is allowed 72 h after completion. Provider requests have no calendar claim. `partner/today` tiles and Needs-you rows are computed from live data on top of the seeded triage rows (see "The web's view logic, in Dart"). Analytics are seeded for the hotel and derived from live data (plus deterministic daily series) for everyone else.

## Round 2 (ADR 0038, owner decisions of 2026-10-29)

Everything below is additive to the contract; the engine and selector equality suites stay green.

* **Sex and the new account** (CA-AUTH-14). `User.sex` (`female` | `male`, optional on the wire), `RegisterInput.sex` required, `UpdateMeInput.sex`, and the new operation `completeProfile` (`POST /me/complete`, body `CompleteProfileInput {name, sex, acceptedTerms, email?}` returning `Me`). `AuthSession.isNewUser` is true from the first code of a number until the account is completed (a registered account is complete from the start, so only its first session is new); a social sign-in starts incomplete as well. Name and sex are editable with `updateMe`.
* **Governorates** (CA-FLT-08, CA-ONB-10, OQ-R2-01). `GET /areas` returns the six official governorates of Kuwait (Capital, Hawalli, Farwaniya, Ahmadi, Jahra, Mubarak Al-Kabeer) with Arabic and English names; the list is **configuration** (a Super Admin setting that can grow to "about eight" or GCC regions), so apps and tests never hard-code the ids. `governorateIds` is on `getHome` (the Brief), `searchVenues` / `countVenues` (explicit selection; `briefGovernorateIds` is the Brief's region), `listServiceProviders` and `WeddingProfile` / `WeddingProfileInput`. Both engines implement the governorate filter (TypeScript `listVenues`, Dart `catalog.dart`): empty = all, several = any, unknown = none; 22 shared engine cases pin it. `areaIds` / `briefAreaIds` / `allAreas` stay (deprecated); a venue's `areaId` is an address line.
* **Partner application** (PA-ACC-07, PA-ACC-08, OQ-R2-03). `chooseAccountType` takes the form (`accountType` `service_provider` or `venue`, business `name` in both languages, up to three `categoryIds` plus `otherCategoryNote`, `governorateId`, `contactName`, `phone`, `email`, `description`, optional `licenceRef`). The fields are optional in the schema (older callers compile), but the mock answers `422 VALIDATION_FAILED` with one `{path, code: "required"}` per missing business field, `too_many` for a fourth category and `unknown_governorate` / `unknown_category`; a service provider needs a category or the Other note. The account starts `under_review` with an application `pending` (`PartnerMembership.application`, `PartnerAccount.application`, `getPartnerApplication`); staff decide through the control endpoint; `rejected` carries `rejectionReason` (`{en, ar}`) and `decidedAt`; `resubmitPartnerApplication` (`PUT /partner/application`, rejected only, else 409 `APPLICATION_NOT_EDITABLE`) edits it and sets it `pending` again with the reason cleared; `accepted` makes the account `active`. **Only an accepted account can create listings**: `createListing` answers `403 APPLICATION_NOT_ACCEPTED` (`params.applicationStatus`) while the application is pending or rejected. Accounts without an application (every seeded partner, hotels, halls and Zahra) count as accepted; the two seeded applicants (`provider_applicant`, `provider_rejected`) are created at every reset by `domain/applications.dart`; any other application is started with `chooseAccountType` (for example as `hotel_non_major`, which adds a second account to that user).
* **No extras on the venue side** (CA-SVC-19). `VenueDetail.extras` and `PackageCatalog.extras` are deprecated and always `[]`; `createExtra` / `updateExtra` still answer (the extra is stored, nothing lists it) and the engine and `quoteVenue` still price an extra when a caller passes one, so old callers keep working. The seeds still hold the extras for the engine cases.
* **Configuration**: `AppConfig.partnerAppUrl` is the store page the Client app's note for service providers links to (CA-SVC-20, OQ-R2-04).

## What is faked (and what replaces it)

OTP and password reset codes (WhatsApp, Resend: the outbox), the payment gateway (MyFatoorah: sessions settle on a timer or by the control endpoint), push (the notification centre is filled by the same events), media upload (signed URL points at `/__mock/uploads/{id}`, nothing is stored; a completed upload reuses a seeded photograph), realtime chat (REST only, `listMessages?afterSeq=`), support and moderation staff (scripted replies and control endpoints), step-up (the tokens are issued but never required), `ghazal_core`'s `ApiProblemCode` only knows part of the contract codes (the rest map to `UNKNOWN`: see requests.md).

## Known differences from the web

What the mock does NOT do like the prototype, and why. Anything not listed here is pinned by `selector-cases.json` or by the engine cases.

| Difference | Why |
|---|---|
| **Arabic text search.** The web's engine helper `normalizeSearch` (`packages/contracts/src/engine/text.ts`) has a range typo in its tashkeel pattern (`[ؐ-ًؚ-ٟۖ-ۭـ]`: the first range runs from U+0610 to U+064B and so eats every Arabic letter), so the web's `listVenues({ query: <Arabic> })` matches every venue and `searchRegions('مشرف')` finds nothing; the Typeahead and CL-DISC-07 avoid the bug with their own `fold()`. The mock follows `fold()` plus the article (`foldSearch`). The engine's `normalizeSearch` in Dart stays equal to the TypeScript one (the engine cases pin the Arabic outputs as `""`), the search handlers do not use it. | Fix in TypeScript: tashkeel is `U+0610-U+061A`, `U+064B-U+065F`, `U+0670`, `U+06D6-U+06ED`, tatweel `U+0640`; then regenerate `engine-cases.json` and update the Dart `normalizeSearch`. `packages/contracts/src` is outside this round's ownership; recorded as an open issue. |
| The text search also matches the **governorate** name (the engine's rule); the web Typeahead lists halls by their own name, their area and the area's aliases only. | The engine rule is the older, documented one (CA-FLT-01). No case depends on it. |
| `audience` of `searchVenues` is the Brief's audience (it prices and ranks) and no longer filters venues; the web's "arrangement" filter is the new `arrangement` parameter. | The web has the two fields apart. |
| Search has no `price-desc` sort. | The web derives it by reversing the price sort on the client; the contract's `VenueSort` has no such value. |
| `getHome` gives `freeCount` `null` without a date (the web counts the non-government halls). The `date` of an item is the Brief date on every rail except `week`, where it is the free day. The "Saved" rail of the Home is built on the device from the wish list, not by the feed. | The contract says `null without a date`; the saved rail has its own operation. |
| `budgetMin` and `budgetMax` of `getHome` and `searchVenues` are accepted and ignored. | The web's Brief carries a budget, but neither `listVenues` nor the shelves read it. |
| **Partner tiles**: `requests` (pending without a counter-offer) and `awaitingClient` are live and equal the web's; `vouchersRedeemed`, `vouchersBought`, `openDatesNext30Days`, `softDateCount` and `unreadMessages` are computed from live data, the web shows the seeded analytics numbers. | The web tiles are fixture constants. |
| **Needs-you order** is the selector's (`needsYou()`: deadline first, awaiting-client rows among the requests); the Today screen's hook ranks the kinds again (requests, visits, messages, reviews, calendar, then the waiting ones). The app can rank by `item.type`. The provider's Needs-you has no listing-decision or voucher-window rows (the web adds them in the screen's hook), and no provider case is in the selector file. | Presentation ranking is the app's job; the provider queue is outside the cases of this round. |
| `listRedeemableVouchers` is ordered by event date; the web's list order is the fixtures'. The selector test compares it as a set. | The web order is arbitrary. |
| Reviews with the same `postedAt` keep seed order; the web venue page has no sort of its own beyond the selector. | Ties only. |
| The **sister venue** has a membership, a name, a role and a pending count and nothing else (no halls, calendar, requests): venue-bound calls in its context are 404. | The web keeps it as demo state (`hotelSettings.sister`). |
| Notification ties reverse only in the **partner** list (the web comparator `a.at < b.at ? 1 : -1` is not a total order). The client list keeps fixture order. | Reproduces the web where the owner looked; the client list has no tie in the story. |
| A voucher **attached to a request** (status `bound`) does not move to another date through `rebindVoucher` (409 `VOUCHER_NOT_USABLE`); only a ready voucher (status `active`) does, and only at its own venue or provider. | The web has no such move: the date of a pending request changes through the venue's counter-offer. |
| The web's `BookingDraft` keeps extras by id and quantity locally; the API input already carried the quantity (`QuoteExtraInput`), so no field was added. | The pilot agents' worry was the draft, not the contract. |
| **Older Brief areas.** The web (`briefGovernorates` in `design/src/system/domain-filters/governorates.ts`) maps a Brief that only has `areaIds` up to the governorates of those areas and narrows by governorate; the mock keeps the API's deprecated behaviour and narrows such a Brief by area. A Brief with governorates is identical in both. The Home distance origin is the web's fixed Salmiya, the mock's too whenever the Brief has governorates. | The apps only send governorates since round 2; the selector exporter writes every Brief as governorates, so no case depends on the difference. Re-run `node tools/export-selector-cases.mjs` after the web's `data.ts` changes. |
