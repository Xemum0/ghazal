# Screen agent brief

> The standing rules for any agent building or changing screens in the Ghazal Design Studio. Extracted from the screens-build workflow; keep it current. Read it fully before touching a screen.

- Project root: /Users/youcefs/Desktop/Desktop/ghzal (absolute paths; your cwd may differ). Never touch "BookingSaaS v2.3 Nulled.rar".

- READ FIRST, in this order: AGENTS.md; design/README.md (the "Add a screen" section is the procedure you must follow exactly, plus routes and the shots tool); docs/design/01-direction.md (BINDING visual direction: Maison identity, Majlis structure, Thread verbs; token tables; component rules; DO/DON'T); docs/engineering/STATUS.md (what exists, known gaps); docs/product/fixtures.md (the seed content and the ONE hero story both apps tell: the client request for 14 Jan 2027 shows up as a pending request in the hotel app); your flow's inventory file (path below) — it lists every screen with requirementIds, states, interactions, contentNotes and navigatesTo; the ADRs named in your task plus docs/decisions/0013 (Arabic voice), 0014 (RTL mirroring), 0010/0011/0012 (formats), 0017 (motion), 0030/0031. Skim design/src/gallery/*.tsx and the system barrels (design/src/system/*/index.ts) to learn what components already exist — REUSE them; do not rebuild what exists.

- IMPORTANT CONTEXT — THE OWNER'S FEEDBACK: the product is NOT a Figma-style board. When the owner opens the prototype they see ONE phone, choose Client or Hotel (a switch above the phone, at the bare URL, built in design/src/shell/Launcher.tsx), and start surfing a real, tappable app. So the click-through experience IS the deliverable: every tap must go somewhere sensible, every sheet must open/close, every flow must end somewhere good (no dead ends), and the first screens a visitor sees must be beautiful. Canvas/inspector views remain only for dev QA; do not spend effort on them. Test your flow the way the owner will: open the launcher, tap through it in Arabic and English.

- EXISTING PARTIAL WORK: an earlier attempt of your flow was interrupted by a usage limit. Files may already exist under design/src/screens/<app>/<flow-id>/ and in your i18n namespace files, possibly unfinished, with type errors, or lower quality than the direction doc demands. READ them first; keep what is good, finish what is missing, fix what is wrong, and bring EVERYTHING to the quality bar. Do not start from zero and do not leave half-finished files.

- YOUR JOB: build EVERY screen of your flow as designed, at premium, production-quality, to the direction doc. Each screen is a file design/src/screens/<app>/<flow-id>/<INVENTORY-ID>.tsx (+ a sibling CSS file with tokens only) exactly per design/README.md. Export `states` for every state the inventory lists that deserves its own frame (loading skeleton, empty, error, offline, success...). Wire the prototype so a viewer can click through the flow in the player (#/play): use useNav() push/pop/replace/switchTab/openSheet/openDialog/toast exactly along the inventory navigatesTo edges, and the prototype store for cross-screen state (auth/guest gating per ADR 0007, brief, compare list, booking draft, hotel request actions with Undo). Screens that are sheets or dialogs must be built as such (kind in the inventory).

- CONTENT: use ONLY the shared fixtures (design/src/mock, re-exporting @gz/contracts) for venues, prices, bookings, requests, people, dates — money in integer fils through useFormat(); NEVER type a price, date or number into a message string; no lorem ipsum, no placeholder names, no invented venues. All user-facing strings live in YOUR i18n namespace files packages/i18n/messages/{en,ar}/<app>-<flow>.json (already created from the template — delete the example keys, add yours; do NOT run new-namespace.mjs or edit other namespaces; words in `common` are reusable). Write the Arabic as a native Kuwaiti-market copywriter would (ADR 0013): not translated word-for-word, warm, precise, gender-neutral where possible, correct plurals, numbers Latin digits. Images only from design/public/images/manifest.json (curated library; check files exist; use alt text from the manifest; no faces).

- DESIGN QUALITY (this is the whole point): every measurement on the 4-pt grid and from tokens (var(--gz-...)); gutter 20; heights 44/48/52/56; one primary action per screen (gold fill, ink label); gold only as a verb (direction doc rule); hierarchy clear at a glance; photography as the hero where it exists; serif display only where the direction doc allows (client: venue names, hero headlines, hero price; hotel: venue names + greeting only); the figures voice for numbers; the khayt/thread and Booking Thread used exactly as specified; real system chrome and safe areas; fluid 360-430; logical CSS properties only; Flutter-translatable subset (flex + gap, px, no grid/calc/rem/filter/blur/blend; sticky only for pinned bars with /* flutter-ok */); motion from tokens with reduced-motion respected; nothing generic or template-like; nothing childish; consistent density between screens of the same flow and with the rest of the app.

- PROCESS (mandatory): (1) plan the flow's screens and their shared local pieces; (2) build all screens; (3) render with `pnpm shots --screen <ID> --lang both --w 390 360` (and every exported state with --state) and LOOK at every PNG with the Read tool — Arabic ones especially; open the flow on the canvas once (#/canvas/<app>?focus=<ID>) via pnpm shots --url-hash to judge it as a sequence; (4) critique ruthlessly like a senior art director + an Arabic/RTL + accessibility lead (misalignment, inconsistent spacing, weak hierarchy, clipped or wrapped text, wrong mirroring, bidi scrambling of prices/phones/dates, cramped touch targets <44, unclear primary action, off-brand look, content that does not make sense in Kuwait); (5) fix; repeat steps 3-5 at least twice; (6) finally run `pnpm typecheck` (ignore errors in files you do not own), `pnpm lint:css` (your files must have 0 warnings), `pnpm i18n:check` (must pass), and click through the flow once with a small playwright-core script or the player to prove the navigation edges work (no dead ends, no console errors).

- OWNERSHIP: you may create/edit ONLY design/src/screens/<app>/<flow-id>/** (including a _components/ folder for flow-local pieces) and your two i18n namespace JSON files. Everything else is single-writer. If you need a new/changed shared component, token, fixture or dependency: build a flow-local version in _components/ and append ONE line to docs/engineering/requests.md with shell `>>` ("- [flow:<app>-<flow-id>] <what + why>"); never edit shared files. If a fixture is missing something the screen needs, file a request and use the closest existing data (never invent data in the screen).

- Do not hand-type or guess localhost URLs; use pnpm shots / node tools/ports.mjs url design. Never kill processes you did not start. Commit nothing. Write files one at a time (no giant single outputs).

- When finished return the report through structured output. Be honest about anything unfinished or compromised.

## Text diet (binding since 2026-10-19: ADR 0034, `docs/design/02-text-diet.md`)

- THE OWNER'S REQUEST: "reduce the text from the app design and make more icons and illustrative without the most need of texts". Every screen you build or touch is judged on how little it says. Read `docs/design/02-text-diet.md` in full before writing a string.
- BUDGETS (EN / AR): screen title 3 words; section title 2 (3 max); button 2, verb first; field label 2; caption or helper 6 / 5 and only when it prevents an error; status = icon + one word; toast 4; state title 4; onboarding 5; list row 3 with no subtitle. At most 35 visible words per screen (45 for a form), excluding authored content and data values. No body paragraphs, except legal consent, cancellation and voucher terms, and error recovery, and those sit behind `InfoButton` (opens `InfoSheet`).
- FACTS ARE ICON + VALUE, NO LABEL: guests, area, session, rating, price, capacity, distance, time left, sections (women, men, mixed) are `FactChip` / `FactRow` with the glyph names of the policy (`users-three`, `ruler`, `sun`, `moon`, `star`, `coins`, `per-guest`, `navigate`, `timer`, `section-women`, `section-men`, `section-mixed`). The label goes in the `label` prop (accessible name).
- USE THE NEW PIECES, DO NOT BUILD LOCAL ONES: `Illustration` (name, size, tone) and the states `EmptyState` / `SuccessState` / `ErrorState` (illustration + title of at most 4 words + ONE action; pass `illustration`, drop `body`; error recovery goes in `detail`), `OnboardingSlide` (illustration + <= 5 words), `IconListRow` (leading glyph, one line, no subtitle), `StatusIcon` / `StatusPill` (icon + one word; time is a `FactChip` with `timer` and `useDuration`), `IconTabs` / `IconSegmented` (glyphs, word only on the selected item), `IconStat`, `IconProgress` and `BookingThread` (glyph per knot, word on the active knot). The gallery pages `#/gallery/diet` and `#/gallery/illustration` show every one in both languages. Pick the illustration by state from the catalogue (`empty-saved`, `empty-messages`, `empty-bookings`, `empty-vouchers`, `empty-visits`, `empty-results`, `empty-notifications`, `empty-listings`, `success-request`, `success-voucher`, `success-booking`, `success-payment`, `success-visit`, `partner-scanner`, `partner-calendar`, `partner-review`, `partner-ads`, `partner-redeemed`, `onboard-compare`, `onboard-dates`, `onboard-voucher`, and the spots for errors: `warning`, `wifi-off`, `shield`, `no-result`, `card`). Need a drawing or glyph that does not exist? Append one line to `docs/engineering/requests.md`, never draw inline.
- ICON-ONLY CONTROLS: only the universal glyphs (heart, share, phone, chat, close, search, filter, calendar, pin, camera, back, more, compare scale), always with an accessible name and a 44 px target. Never for money, accept or decline, delete, pay, confirm: keep one word.
- ARABIC IS SHORTER STILL: no filler, verbal nouns, no repeated honorific in every line; do not translate what the glyph already says.
- MEASURE AND REPORT: `node design/scripts/wordcount.mjs --lang both --only <your ID prefixes>` before and after; the targets are at least 45% fewer words per screen in EN and AR (at least 55% on the hero screens listed in the policy). Requirement coverage must not drop: every requirement ID in a screen header keeps a visible, reachable home. Report the before and after numbers (EN and AR) in your hand-back. Unused i18n keys in your namespace are removed in the same change (`pnpm i18n:check` stays green).
